Tasks

Tasks is a program that runs coding agents against your GitHub issue tracker. It reads your open issues; for each one you queue, it sends an agent to explore the codebase and write a spec, waits for you to approve that spec, sends a second agent to implement it, opens a pull request, and closes the issue once the work is actually on main. It runs on your own Mac, on repositories you point it at, with your own API key.

Read this first

Tasks runs coding agents against your repositories with nobody in the loop between a decision and the act. Before you point it at anything, know what it does.

  • The agents run unattended, with permission checks off. Scouts and Builders are Claude Code processes started with --dangerously-skip-permissions (images/scout/Dockerfile, images/builder/Dockerfile): inside their VM they run whatever commands they decide to run, and nothing asks you first. The VM is the boundary, and it is a real one — each is ephemeral, and the credentials a run is given reach Anthropic and read the one repository it was dispatched for. Agents cannot push.
  • The server can. On an agent's say-so, under its own GitHub credential, while you are not watching, it pushes branches, opens pull requests, merges them, comments on issues and closes them. All ten capabilities in the orchestrator's charter ship live and uncapped — each set so by the migration that adds it (crates/tasks/migrations/0016_charter_live.sql and after) — no daily limit, no pre-approval gate, nothing that stops at the tenth merge of the day. The charter is a kill switch, not a promotion ladder, and the append-only decisions ledger is something you read afterwards. Any one capability can be switched off on its own, which is how you keep the pipeline and merge by hand: 
    curl -X POST localhost:4800/charter/land_builds \
     -H 'content-type: application/json' -d '{"level":"off"}'
  • The local API has no authentication. Anything running on your machine that can reach port 4800 can drive the pipeline — start a Scout, start a Builder, merge a pull request — and it is recorded as you, because a caller that does not identify itself is read as the human and the human is never gated. Web pages are refused (crates/tasks/src/loopback.rs), but that guard is about pages, not about processes.
  • The orchestrator is not in a VM. It is a Claude Code agent in an ordinary child process on the machine running the server, and what it may do is whatever ORCHESTRATOR_CMD allows. The default is curl and nothing else; pointing ORCHESTRATOR_WORKDIR at a checkout and adding --dangerously-skip-permissions, which docs/operating.md describes as a supported way to run it, makes it a full developer agent on your host.

The server boots paused, so nothing moves until you say so. Point it at a repository you would not mind rewriting — a fork, a scratch repo, something where a bad pull request costs you a click. This is software one person wrote to run on his own machine, published in case it is useful to you: there is no warranty, nobody is on call, and if it breaks something of yours, fixing it is your job. The LICENSE says the same thing in the legal register.

How it works

The architecture is a double diamond: explore widely, decide once, build narrowly, ship.

GitHub issues ──▶ backlog ──▶ queue ──▶ SCOUT ──▶ spec ──▶ review ──▶ BUILDER ──▶ PR ──▶ merged ──▶ done
                                     (parallel)          (human or            (serial)
                                                        orchestrator)
  • Scouts run in parallel, each in its own ephemeral VM. A Scout explores the codebase and writes a spec — a text document saying what to build and how. The spec is the deliverable; the Scout's code is thrown away.
  • Specs land in a review queue. You approve, request revision, or reject. Nothing is built from a spec nobody ruled on.
  • Builders run serially, one at a time. A Builder is given approved specs and never Scout code — the information barrier is deliberate, and it is why a Builder can batch several specs onto one branch. It implements them on a fresh branch and opens a pull request carrying its own test verdict.
  • A merge watcher confirms the work actually reached the trunk, rather than trusting GitHub's merged flag, which only means a branch took the commit. The issue closes when the work is really on main, so done means shipped.

Beside the pipeline sits an orchestrator: a Claude Code agent that wakes on a tick, reads a brief of everything owed a decision, and acts — queueing tasks, reviewing specs, dispatching builds, commenting upstream, landing pull requests. What it may do is a charter of nine independently switchable capabilities, each off, shadow or live, writable only by you and enforced by the server rather than by its prompt. Every act it takes lands in an append-only decisions ledger with the rationale it gave, which is what you read afterwards and what you reverse.

What it looks like

Before you start

  • A Mac with Apple silicon. The VMs are apple/container's, so this half is macOS only.
  • apple/container installed and its services started. container system start — having the CLI is not the same fact as having the runtime running, and only the second one starts a VM.
  • An Anthropic API key. Every agent run is metered to you. A pipeline left running is not cheap: a Scout and a Builder each get a budget measured in model-hours, and the orchestrator wakes on a tick whether or not anything happened.
  • A GitHub token that can push. The server pushes branches, opens pull requests and closes issues under it. Agents never hold it.
  • Rust, edition 2024, plus the Linux cross toolchain the VM images are built with (rustup target add aarch64-unknown-linux-gnu and a matching linker). Until there is a release, you build all of it yourself — the server, the app and the container images.
  • About 22 GB of RAM free at the default VM sizes: two Scouts at 6144 MB each, one Builder at 8192 MB, plus the container runtime's own builder. Fewer concurrent Scouts is the knob if you have less.

Getting it

There is no release yet. When there is one it will be a signed and notarized Mac app with the server inside it, published at the repository's releases page. Until then there is nothing to download and the way to run it is to build it.

git clone https://github.com/iamnbutler/tasks
cd tasks
cargo build -p tasks
export PATH="$PWD/target/debug:$PATH"

tasks secrets init                     # sealed credential store
tasks secrets set anthropic-api-key    # value on stdin
tasks secrets set github-token
cp .env.example .env
cargo run -p tasks -- add-project owner/repo
make images                            # the Scout and Builder VM images

tasks vm-pool                          # terminal 1: the VM pool
make serve                             # terminal 2: the server
tasks doctor                           # terminal 3: is this machine ready?

The full sequence, with what each line is for and what goes wrong without it, is in the README. make images has no progress bar and takes a while; the long silences are cross-compiles.

The server boots paused, and ingested issues land in a backlog that is never dispatched from. Pointing Tasks at a repository with ten thousand open issues gives you ten thousand backlog rows and zero agent runs — work moves only for the tasks you queue, once you put the pipeline in play. That is not a rate limit you can raise; it is the shape of the thing.
