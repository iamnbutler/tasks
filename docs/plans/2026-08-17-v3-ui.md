# v3 UI: persistent three-pane workspace

Branch: `v3-ui`. This is a **UI pass over existing data** — the one hard rule,
stated by Nate during the interview: *no new server features ride along*.
Where the design shows something the server cannot feed yet, we build the
visual with an honest empty state and write the gap up here as a follow-up,
we do not implement the feature. Iteration is expected; the branch exists so
the design can move without ceremony.

Reference design: the Figma frames from 2026-08-17 (dark, gruvbox,
monospace-forward). Some frames contain One Dark stragglers from an
unfinished pixel pass — ignore those; the palette is gruvbox, and gpuikit's
`Theme::default()` already *is* Gruvbox Dark.

## 1. The shape

The current app is five sections behind an icon nav (⌘1–5), one on screen at
a time, with a right-sidebar inspector. That model dies. The new shape is
three persistent panes:

```
┌────────────────────────────────────────────────────────────────────┐
│ titlebar: ‹ project-switcher …        ▷ ⏸ ⋮       (drag region)    │
├──────────────┬──────────────────────────────┬──────────────────────┤
│ LEFT RAIL    │ MIDDLE                       │ RIGHT                │
│              │  ← → │ tab │ tab │ tab │ tab │                      │
│ All Tasks    │                              │  orchestrator chat   │
│ Tasks (tree) │  selected task's tabs,       │  (always on screen,  │
│  …           │  or the All Tasks table      │   ⌘R to hide)        │
│ ──────────   │                              │                      │
│ Awaiting     │                              │                      │
│  Feedback    │                              │                      │
│ ──────────   │                              │  ┌────────────────┐  │
│ (future:     │                              │  │ composer        │ │
│  Automation, │                              │  │ gauge · send    │ │
│  Suggested)  │                              │  └────────────────┘  │
│ [composer]   │                              │                      │
└──────────────┴──────────────────────────────┴──────────────────────┘
```

Section-by-section fates, per the interview:

| Today | In v3 |
| --- | --- |
| Home | **Deleted.** Home is gone or will be soon; nothing migrates. |
| Tasks | Becomes the **All Tasks** middle view (the table, restyled). |
| Queue | Becomes the **left-rail tree** (ordering) — the six-band table dies. |
| Activity | **Deleted from the workspace.** Folds into the orchestrator side eventually; not rebuilt in this pass. |
| Chat | Becomes the **right pane**, always on screen. |
| Detail inspector | Content moves into the middle column's **Overview/Brief** tabs. |

Windows that are not the workspace — New Issue (⌘N), Add Repo (⇧⌘N), Server,
About — and the palettes, row menu, and menu bar all survive as they are,
modulo command-table edits (§7).

## 2. Left rail

### 2.1 Scope: one project, global feedback

The titlebar project switcher scopes the **Tasks tree** to one project at a
time. **Awaiting Feedback is deliberately cross-project** — attention must
not hide behind the switcher — so its rows carry a `Project ›` prefix, as in
the design (`ToyUI › Fontkit-based text rendering`).

Consequence for reordering: today the Queue section refuses to filter by
repo because both reorder endpoints are bulk replaces computed from the
server's full list order. That rule survives scoping: a drag in a scoped
tree still computes its payload from the **server's complete order with one
row moved relative to its visible neighbours' global positions** — never
from display order, and never from the scoped subset alone. The existing
`task_queue_base` (queue.rs) logic is the porting target; it already works
this way.

### 2.2 All Tasks

A static item above the tree ("All Tasks"), not a group. Clicking it swaps
the middle pane to the All Tasks table (§4.5). This is the only place
backlog lives, and — since the tree below shows only picked-up work — the
place where queueing happens (row menu / ⇧⌘U, as today). This preserves the
house invariant: bulk intake never auto-dispatches; queue membership stays
an explicit act.

### 2.3 The Tasks tree is the queue

Rows are tasks that are somewhere in the pipeline, in attention order —
the same band order the Queue section uses today, drawn as one continuous
list without band headers:

1. Scouting (running)
2. Building
3. Awaiting merge
4. Queued (up next)
5. Ready to build (approved spec, unbatched)

**Visual position is queue position.** Dragging a row up means "sooner".
The two-orderings reality underneath doesn't change:

- Draggable: Queued rows (`tasks.manual_rank` via `POST /queue/reorder`)
  and Ready-to-build rows, each within their own stratum — the existing
  `TaskQueueDrag` group separation carries over.
- Fixed: Scouting / Building / Awaiting-merge rows are neither drag sources
  nor drop targets. Today's lock-icon-with-reason tooltip carries over.

Row anatomy: `title  #number` left, one **state glyph** right:

| State | Glyph |
| --- | --- |
| Scouting / Building | animated spinner (accent-tinted; the design's ring) |
| Queued / Ready to build | static queue-position affordance (drag handle on hover) |
| Awaiting merge | static badge glyph |
| Needs revision / failed-out | the crossed-circle, `danger`-tinted |
| Done | checkmark — but done tasks retire from the tree (they live in All Tasks behind the existing Show-Done toggle) |

Colors come from the existing `task_state_color` vocabulary; glyphs are the
design's, not new semantics. The elapsed-clock affordance from the Queue's
Running/Building rows moves into the row's tooltip rather than a column.

Subtask child rows in the design (`CheckboxRow`, `The Basics`, the
`Waiting on #41` dependency) are **out of scope** — there is no subtask
entity and we are not inventing one in a UI pass. The tree renders flat
task rows until subtasks exist.

### 2.4 Awaiting Feedback

A separate section under the tree, dashed-rule separated (per design).
Content: **specs awaiting review** — the `InReview` set, i.e. today's
"Needs you" band — ordered by `spec_queue.rank`, cross-project, with
project prefixes. Clicking a row selects the task and opens the middle
column on the **Brief** tab, where the review form lives (§4.2).

Not included (deliberately, per interview): parked `awaiting_merge`
batches, `needs_revision`, the obligations feed. Those keep reaching the
human through the orchestrator. Drag-to-rank within this section
(`POST /spec-queue/reorder`) is a fast-follow, not milestone work.

### 2.5 Bottom composer

The design's "Add another task" box is a **shortcut into the ⌘N flow**, not
a new path: same draft-to-orchestrator message (orchestrator titles the
issue and files it via `POST /issues` with the pinned `project_id`), same
refusal to send while the project target is ambiguous, same jump-to-chat on
send — except "jump to chat" is now free, the chat is already on screen.
Reuse the workspace-owned `InputState` pattern so drafts survive. ⌘↩ sends
(house rule: every composer is `SubmitOn::CmdEnter`).

### 2.6 Titlebar

- Left: back-chevron is **middle-column history back** (§4.6) in the design;
  keep the sidebar toggle too (⌘B still works).
- Project switcher popover: unchanged mechanics (it stays a popover — the
  menu-bar leak that forced that is still real).
- Right: **play/pause = global mode**, per the interview — not project
  status. Project pause/archive stays in the switcher/overflow, off the
  titlebar. Stop remains menu/palette-only (unbound verb that changes the
  world, as today). Refresh and the banner-precedence ladder carry over;
  the banner slot stays at the left rail's bottom.
- Automation / Suggested Tasks / voice mode appear in the design and are
  **explicitly not this pass**. Leave collapsed-section placeholders out
  entirely; add nothing.

## 3. Right pane: orchestrator chat

The existing Chat section moves here wholesale — the `chat_log` row model
and its three invariants, the virtualized `gpui::list` with tail-follow,
markdown cache, tool-group coalescing, hover affordances, the
clock-not-spinner footer, jump-to-newest. None of that is redesign work.

- **Always on screen; ⌘R toggles it.** Convenient collision: ⌘R already
  toggles the right dock. The binding survives, the dock's content changes.
- The **context gauge** (in-flight work on this branch's working tree:
  `context_gauge.rs` + chat-header rendering + its migration) lands as
  designed — collapsed `Opus 5 ▬▬▬░░ 491.5k / 1M · 49%` strip on the
  composer per the mock, expandable breakdown popover. That work is its own
  change; v3 just inherits its placement.
- Chat width cap (768px) stays; the pane is resizable via the existing
  sidebar drag handle.
- The old Chat-tab elapsed badge is obsolete (no more section nav); the
  live-tick clock already lives in the footer status line.

## 4. Middle column

Driven by a selection model: selecting a task (tree, feedback list, All
Tasks row, palette, chat event row) shows that task's tab set; selecting
All Tasks shows the table. Tab strip uses gpuikit `tabs`.

Four tabs per task, **Overview is the default** on open:

### 4.1 Overview

The landing tab — absorbs most of today's inspector (detail.rs):

- Title, `#number`, state badge + GitHub-state badge, labels, updated-at.
- **Orchestrator Context** block, styled per the design (small-caps header,
  italic body). This is the one *visual-only* feature: the data will come
  from a future one-off completion generated from the orchestrator's
  context (endpoint design TBD — see §8). Until then the block renders only
  when content exists, which is never; ship the styling behind an honest
  empty state ("not yet generated", muted) so the layout is real and the
  follow-up is purely server-side.
- Issue body (markdown), when no spec exists yet.
- The recovered-implementation (bundle) block, verbatim from detail.rs —
  amber, `git fetch` command, armed delete.
- State actions (Add to Queue / Scout Now / Remove from Queue / Open on
  GitHub) and the Build Now form, as today. Buttons should become gpuikit
  `button()` — the app currently hand-rolls five button implementations.

### 4.2 Brief

The spec — the scout's deliverable, or the human-authored one:

- Latest spec as markdown, `SPEC · <COMPLEXITY>` header, `· HUMAN-AUTHORED`
  marker when `session_id` is null (build-now provenance), falling back to
  nothing (tab disabled/empty-state) when no spec exists.
- **The review form lives here** when a spec is pending: Request Changes /
  Ask Orchestrator / Reject / Approve (⇧⌘A), exactly today's four exits.
  The spec is the thing being ruled on, so the ruling sits next to it.
- Revision notes, when the task went `needs_revision`, so a re-review sees
  what was objected to.

### 4.3 Agent feed

The tab the interview flagged as the missing capability: *seeing the
context of a running VM*. Finding from the code walk — **the server surface
is already complete**, this is client work only:

- `GET /sessions/{id}/transcript/stream?since=` and
  `GET /builds/{id}/transcript/stream?since=` exist, with backfill-then-live
  semantics, and `tasks-client` already wraps both
  (`stream_transcript` / `stream_build_transcript` → `TranscriptTail`).
- What arrives is **raw Claude Code stream-json lines** (`TranscriptLine`,
  dense per-owner `seq`), not parsed events. The app must parse each line
  just enough to render: assistant text deltas as markdown, tool calls as
  coalesced groups (reuse the chat's tool-group idiom), result/system
  records as quiet one-liners, unparseable lines as raw monospace.
- Honor the transcript capture contracts: lines starting with the
  `"[tasks: truncated N bytes]"` prefix render as a truncation notice, and
  the inline `"[tasks] N transcript line(s) dropped here"` marker renders
  as a seam, not as agent output.
- Feed selection: the task's live run if one exists (scout session or
  build), else the most recent concluded run's transcript (both catch-up
  GET routes exist). A small run picker if the task has history.
- Lifecycle: open one tail per *visible* feed, torn down when the tab or
  task deselects — not one per task. Each SSE stream is an OS thread today
  (state.rs's two streams); the feed should reuse that pattern but must not
  accumulate threads as the user browses. Server-side this is safe: streams
  are severed at shutdown by design (`CONNECTION_GRACE`), and an SSE client
  resumes from `since`.

This is the riskiest tab (a stream-json renderer is real work); it is also
the highest-value one. Spike it in-app; if the renderer stalls, the
fallback that still ships value is raw-line tailing with truncation/drop
contract handling, upgraded to parsed rendering after.

### 4.4 Changes

Backed by **build artifacts, not GitHub** (interview decision; house rule —
never persist GitHub-owned facts, and a PR needn't exist yet). What the
server can feed today: the task's builds with branch, PR number/URL when
opened, and the build summary (`SUMMARY.md` — which is also the PR body —
including the `Verification: PASSED|FAILED|NOT RUN` trailer, rendered as
the claim it is, with attribution). So this pass ships:

- Per-build card: branch, status, PR link when open, summary markdown,
  verification trailer surfaced as a labeled line.
- The bundle block cross-links here when a rejected bundle exists.

A real changed-files/diff view needs a server endpoint that reads the
build's branch (e.g. files + patches derived from the bundle or branch at
request time). That is **server work, therefore a follow-up** (§8), and the
tab's layout should leave room for it (file list left of / above patch
view) without blocking on it.

### 4.5 All Tasks view

Today's Tasks table, restyled to the design's list: `#number · title ·
[repo when ambiguous] · state badge · updated`, repo-filter aware,
client-side done-archive behind the counted footer toggle (⇧⌘D), row menu
on right-click, row click selects the task (opens Overview). Backlog rows
still show no badge — absence of pipeline state reads correctly as "not
picked up". This is where Queue/Scout-Now/Build-Now verbs reach backlog.

### 4.6 History

The design's ‹ › arrows: a selection-history stack for the middle column
(task selections + All Tasks), like a browser. ⌘[ / ⌘] bindings. Depth ~50,
in-memory, per-window. New selections truncate the forward stack. This is
new but small and pure — model it as a unit-testable struct like
`chat_log`.

## 5. Theme & components

**Theme: no fork.** The design is gruvbox; gpuikit's `Theme::default()` is
Gruvbox Dark, and the app already runs it. The theming work is a **delta
check, not a build-out**: as each surface is implemented, missing tokens
(if any) get added *in gpuikit* — per the interview, "the whole theme
should be in gpuikit". Candidates to watch: tab active/inactive treatment,
dashed-separator color, the tree's fixed-row lock tint. Badge colors, the
four gauge band colors, and status hues all exist already. One Dark
stragglers in the mock are noise.

**Component sourcing** (interview: use gpuikit where we can; spike locally,
generalize later):

| Need | Source |
| --- | --- |
| Tab strip | gpuikit `tabs` (unused today — adopt) |
| Buttons | gpuikit `button()` / `icon_button()` — retire the five hand-rolled implementations |
| Empty states | gpuikit `empty()` (icon/title/description/action) |
| Badges | keep local `status_badge` semantics; consider gpuikit `badge()` for rendering |
| Tree rows | **local spike** — gpuikit has no tree; its `list` is uniform-height only, which suits flat task rows fine, but drag-reorder needs `sortable` |
| Drag reorder | local `sortable.rs`, already tracked for upstreaming (gpuikit#866) |
| Sidebar/docks | local `sidebar.rs` (gpuikit has none); reused for left rail and chat pane |
| Titlebar | local `titlebar.rs` (platform chrome) |
| Markdown | gpuikit markdown via the local cache + `markdown_block` styling |
| Inputs | gpuikit `InputState` + local `text_field` wrapper until the zero-height single-line fix ships upstream |

**Known gpuikit sharp edges to carry:** single-line `input()` lays out at
zero height (the local `text_field.rs` wrapper is the workaround; likely
fixed in the local gpuikit checkout — note the **registry 0.7.0 and
`~/Code/gpuikit` have diverged** while sharing a version number, so any
upstreaming lands in the checkout and needs a release/bump to reach this
app); the markdown `md-run-N` id collision workaround (the `div().id(…)`
wrapper) must survive any markdown re-plumbing; `palette::bind_keys` after
`bind_input_keys`, `commands::bind_keys` before `menus::set` — both
ordering constraints in `main.rs` are load-bearing.

## 8. Follow-ups (documented, not filed — per interview, doc only for now)

1. **Orchestrator Context generation.** A one-off completion, somehow
   seeded from the orchestrator's ambient context, producing a per-task
   blurb ("A base component task… scoped deliberately…"). Needs an
   endpoint + storage + a decision about regeneration cadence and
   charter-gating (it writes, so presumably `comment_on_work`-adjacent).
   Design is open — Nate: "I'm not exactly sure how it's gonna work yet."
   UI ships dark until this exists.
2. **Changed-files endpoint** for the Changes tab: server-side file/patch
   derivation from a build's branch or bundle, computed at request time
   (never persisted — GitHub-owned facts stay unpersisted; branch contents
   are Tasks-owned but stale-able, so derive on read).
3. **Subtasks** as a first-class entity (the design's child rows,
   checklists, `Waiting on #N` dependencies). Big; touches server model,
   orchestrator authority, and the tree UI.
4. **Spec-queue drag-to-rank** inside Awaiting Feedback.
5. **Activity → orchestrator tab**: fold the event feed into the right
   pane (a filter or interleaving), then delete the endpoint's last app
   consumer.
6. **Automation / Suggested Tasks / voice mode**: future design work,
   deliberately untouched.
7. **Upstreaming**: `sortable` (gpuikit#866), the single-line input fix
   (unify the diverged 0.7.0 trees and release), possibly the markdown
   cache.

## 9. Build order

All on `v3-ui`, each milestone leaves the app runnable (`make app-check` +
`make app-test` green — both work from a Linux agent VM; visual checks are
`make app` on the Mac). Sequenced so the riskiest unknown (agent feed) has
a working shell under it early, and deletions come last:

1. **Frame swap.** Three-pane layout: chat rendered in the right dock
   permanently (⌘R toggles), middle pane host with tab strip + selection
   model + history struct, left rail skeleton (All Tasks item + flat task
   list, no drag yet). Old sections still compile but are unreachable from
   nav. The app is already fully usable at this point via All Tasks + tabs.
2. **Left rail, complete.** Tree in attention order with state glyphs,
   drag-to-rank with server-order payload math ported from queue.rs,
   fixed-row locking, Awaiting Feedback (cross-project, opens Brief),
   bottom composer wired through the orchestrator flow, titlebar
   play/pause + history chevrons.
3. **Middle tabs: Overview + Brief.** Port detail.rs content into the two
   tabs (actions, forms, bundle block, review form on Brief), orchestrator-
   context block with empty state, All Tasks table restyle.
4. **Agent feed.** Transcript tail client (one live tail, lifecycle-bound
   to visibility), stream-json line renderer with the truncation/drop
   contracts, run picker. Raw-line fallback is the de-risk path.
5. **Changes tab + deletions + polish.** Build cards with verification
   trailer, then delete Home/Activity/Queue/Detail/section-nav, command
   table edits, gpuikit adoption sweep (tabs/buttons/empty), theme delta
   check against gpuikit, final visual pass against the mocks.

Invariants that must survive every milestone: reorder payloads computed
from server order; bulk intake never auto-dispatches (All Tasks is the only
backlog surface, queueing stays explicit); chat_log's three invariants; the
main.rs binding-order constraints; drafts owned by the workspace so no
composer loses text on dismiss.
