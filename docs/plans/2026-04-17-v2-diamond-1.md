# v2: Diamond 1 end-to-end (first PR scope)

Scope for the first v2 PR: prove the Diamond 1 loop works reliably end-to-end,
with the orchestrator judging priorities and populating a reviewed spec queue.

## In scope

- Ingest GitHub issues as tasks (poll, normalize)
- Orchestrator loop (Claude Code, not a custom agent layer)
  - Pick next task from the task list (priority judgment)
  - Dispatch a Scout VM via vm-pool
  - Review returned specs (approve / request revision / reject / re-explore)
  - Rank the spec queue and mark the next item for implementation
- Scout execution in a VM
  - Container image with Claude Code + git + cargo/tooling
  - Claude Code runs headless with the issue + spec template as prompt
  - Scout implements against a throwaway branch, runs tests/lint, writes `spec.md`
  - Supervisor reports the spec back to tasks
- Persistence (SQLite)
- HTTP API to observe tasks, sessions, specs, spec queue
- Operating mode: Play / Pause / Stop (just enough to halt the loop)

## Out of scope (deferred to later PRs)

- Diamond 2 (Builder) — no implementation agent, no PR creation
- Change Queue / merge flow
- "Automations" (non-task agent work)
- Feedback loops beyond the Scout → Spec path
- External clients (web, desktop) — this PR ships server + HTTP API only
- Fancy prioritization heuristics beyond what the orchestrator LLM decides
- Historical v1 data migration

## Architecture

```
GitHub Issues
     │ (poll)
     ▼
┌────────────┐     pick next         ┌──────────────┐
│ Task Store │◀────────────────────── │ Orchestrator │
└────────────┘                         │   (Claude)   │
     │                                 └──────────────┘
     │ dispatch                                ▲
     ▼                                         │ review
┌────────────┐    VmCommand/Event    ┌──────────────┐
│  vm-pool   │◀─────────────────────▶│   Scout VM   │
│ (external) │                        │  (Claude CC) │
└────────────┘                        └──────────────┘
                                             │ spec.md
                                             ▼
                                      ┌──────────────┐
                                      │  Spec Queue  │─── HTTP/SSE ──▶ external clients
                                      └──────────────┘
```

The tasks binary is a server. It embeds:
- GitHub poller
- Orchestrator loop
- vm-pool client (talks to the running `vm-pool` service over its Unix socket)
- HTTP API + SSE

## Data model (SQLite)

```
projects            id, repo_owner, repo_name, added_at
tasks               id, project_id, gh_issue_number, title, body, labels, state, priority, ingested_at
sessions            id, task_id, vm_id, branch, status, started_at, completed_at, exit_reason
specs               id, session_id, task_id, content (markdown), complexity, files_touched (json), created_at
spec_queue          spec_id, status, rank, approved_at, feedback, blocking_dependencies (json)
events              seq, timestamp, payload (json)            -- append-only
modes               singleton: mode (play/pause/stop), updated_at
```

Status enums:
- `sessions.status`: `running | scout_succeeded | scout_failed | cancelled`
- `spec_queue.status`: `pending_review | approved | needs_revision | blocked | rejected`
- `tasks.state`: `new | scouting | spec_ready | queued | done | rejected`
  (we don't advance past `queued` in this PR — Builder is out of scope)

## vm-pool protocol (tasks-specific AppProtocol)

```rust
pub struct TasksProtocol;
impl vm_pool_protocol::AppProtocol for TasksProtocol {
    type Command = ScoutCommand;
    type Event = ScoutEvent;
}

pub enum ScoutCommand {
    Start {
        task_id: String,
        repo_clone_url: String,
        base_branch: String,
        issue_body: String,     // rendered prompt for Claude Code
    },
    Cancel,
}

pub enum ScoutEvent {
    Started,
    Progress { line: String },           // stdout/stderr line from Claude Code
    ImplementationFinished { branch: String },
    TestsResult { passed: bool, output: String },
    Completed { spec_markdown: String, files_touched: Vec<String> },
    Failed { reason: String },
}
```

## Scout VM runtime

- Image: `agent:v1` (new — baked with git, cargo, Claude Code CLI, supervisor as PID 1)
- On `Start`:
  1. Supervisor clones the repo with `--branch <base>` into `/workspace`
  2. Creates throwaway branch `scout/<task_id>-<uuid>`
  3. Writes prompt file with issue body + spec template instructions
  4. Runs Claude Code headless: `claude --headless --allow-all < prompt.md`
  5. After exit, reads `/workspace/SPEC.md` if present, relays as `Completed`
  6. If Claude Code exits non-zero or no SPEC.md, relays `Failed`

Claude Code is told to:
- Implement the change
- Run tests, lint, typecheck
- Write `SPEC.md` in the structure the RFC specifies
- Do not create a PR or push anywhere

## Orchestrator

A **single persistent Claude Code session**, driven via the Claude Agent SDK,
that participates in the system over time rather than being called as a
stateless RPC. Its context accumulates: which tasks are in flight, recent
decisions it made, patterns it noticed across scouts.

### How it connects to the system

- **MCP server on the tasks side** exposing read + action tools:
  - Reads: `list_tasks(filter)`, `task_detail(id)`, `running_sessions()`,
    `spec_queue()`, `spec_detail(id)`, `pool_status()`, `recent_events(n)`
  - Actions: `dispatch_scout(task_id)`, `cancel_scout(session_id)`,
    `approve_spec(id)`, `revise_spec(id, feedback)`, `reject_spec(id, reason)`,
    `re_explore(task_id, notes)`, `set_queue_rank(ordered_ids)`, `pause()`,
    `resume()`

- **Event-driven notifications** — when state changes (issue ingested, scout
  completed, scout failed, VM slot opened, queue changed), the server pushes a
  short message into the session. The orchestrator decides what to do next:
  may query more state, take multiple actions, or do nothing. Notifications
  are small pointers ("scout 17 completed, task 42, spec available"), not full
  payloads — the orchestrator pulls detail via tools when it needs it.

- **System prompt** with durable principles (prioritization guidance, spec
  quality bar, how to handle ambiguity, when to pause). Evolving — committed
  to the repo so behavior is reviewable.

### Where it runs

In its own long-lived VM via vm-pool — same infrastructure as scouts,
inspectable, restartable. If the orchestrator VM dies, the session is
re-established and caught up via `recent_events` on the next tick. The server
keeps the authoritative state; the orchestrator is stateless across restarts.

Fallback if VM-in-VM proves awkward: run on the host. Decision deferred to
step 7.

### Reliability

- Tool calls are transactional against SQLite
- Notification queue is durable — if the orchestrator is down, events buffer
- A tool call that the orchestrator makes when confused (e.g., approving an
  already-approved spec) is a no-op, not an error — the session can always
  catch up
- Hard cap: if the orchestrator makes no progress for N minutes (no tool
  calls), the server logs an event and pauses

## Crate / module layout

Single crate `tasks` with modules. (Following the vm-pool lesson: consolidate
until there's a reason to split.)

```
crates/tasks/
├── Cargo.toml
├── src/
│   ├── main.rs              # binary entry point
│   ├── lib.rs
│   ├── models.rs            # Task, Session, Spec, SpecQueueEntry, Mode, ids
│   ├── store.rs             # SQLite: migrations, queries
│   ├── events.rs            # append-only log + broadcast
│   ├── github.rs            # GraphQL client, polling, issue → task normalizer
│   ├── vm.rs                # vm-pool client wrapper + TasksProtocol
│   ├── scout.rs             # Scout dispatcher: VM allocation, prompt rendering
│   ├── orchestrator.rs      # persistent Claude Code session + notification loop
│   ├── mcp.rs               # MCP server exposing tasks tools to the orchestrator
│   ├── queue.rs             # spec queue state transitions, ranking persistence
│   └── server.rs            # HTTP API + SSE
└── tests/
    └── integration.rs       # end-to-end: poll → dispatch → spec → queue
```

If `tasks-protocol` ends up being needed by external Rust consumers, extract it later.

## Implementation order

Each step is self-contained with its own test.

1. **Skeleton + models + store**
   - Cargo.toml, binary stub, SQLite schema + migrations, model types
   - Test: open a fresh DB, run migrations, insert a task, read it back

2. **Events log**
   - Append-only event table + in-memory broadcast channel
   - Test: append, subscribe, receive

3. **GitHub polling**
   - GraphQL client for issues, polling loop, normalizer
   - Test: use `mockito`? No — spin a local HTTP server that returns canned GraphQL responses
   - Produces `tasks` rows

4. **vm-pool client wrapper**
   - Connects to vm-pool Unix socket, implements `TasksProtocol`
   - Test: against a running `vm-pool-service` + a fake scout supervisor binary that echoes canned events

5. **Container image (`agent:v1`)**
   - Dockerfile, supervisor-with-Claude-Code entrypoint, `make image`
   - Test: run the image, send `ScoutCommand::Start` against a trivial test issue/repo, observe `Completed` event. Blocks on having a real repo to test against — use a fixture repo committed under `tests/fixtures/`.

6. **Scout dispatcher**
   - Wires task → vm-pool allocation → prompt rendering → receive Completed → persist spec
   - Test: end-to-end with fixture repo

7. **MCP tool server**
   - Exposes read + action tools backed by the store
   - Test: connect an MCP client, exercise each tool, verify state transitions

8. **Orchestrator session**
   - Long-lived Claude Code session driven via the Agent SDK
   - Notification queue (durable, backed by the events table)
   - System prompt committed to repo
   - Decide: host process vs. dedicated VM (default: VM — fall back to host if blocked)
   - Test: drive the full loop with a scripted stand-in agent (a real subprocess,
     configured via `ORCHESTRATOR_AGENT_BIN`) that calls MCP tools deterministically.
     Verify: task picked → scout dispatched → spec reviewed → queue ranked.

9. **HTTP API + SSE**
   - Routes: `GET /tasks`, `GET /sessions`, `GET /specs`, `GET /spec-queue`, `GET /events` (SSE), `POST /mode`
   - Test: spin the server, hit endpoints, verify

10. **Wire-up in `main.rs`**
   - Load config, open DB, start poller, orchestrator loop, HTTP server
   - Integration test: drive the full loop against a fixture repo + fake orchestrator binary

## Testing approach

Same principle as vm-pool: **no mocks**. Everything uses real processes or real
SQLite DBs (file-backed tempfiles).

- GitHub tests: local HTTP server returning canned GraphQL JSON
- vm-pool tests: spin a real `vm-pool-service` in a tempdir, point the client at it
- MCP tests: real MCP client against the real MCP server, verify tool behavior
- Orchestrator tests: a scripted stand-in binary (real subprocess) that acts as
  the agent — reads notifications, calls MCP tools in a deterministic pattern
- Scout tests: real container via vm-pool against a committed fixture repo

## Config

- `TASKS_DATA_DIR` — SQLite + event logs (default: `~/.local/state/tasks-v2/`)
- `TASKS_SERVER_PORT` — HTTP API (default: 4800)
- `GITHUB_TOKEN`, `ANTHROPIC_API_KEY` — unchanged
- `VM_POOL_SOCKET` — path to vm-pool's Unix socket (default: `/tmp/vm-pool.sock`)
- `ORCHESTRATOR_MODEL` — passed to Claude Code invocation

v1 data dir (`~/.local/state/tasks/`) is untouched; v2 uses `tasks-v2`.

## Operating mode

Minimal implementation:
- `Play` — poll, dispatch scouts, review specs
- `Pause` — keep polling + persisting, but do not dispatch new scouts and do not
  auto-advance spec queue entries; running scouts complete normally
- `Stop` — cancel all in-flight scouts and stop polling

## Open questions

1. **Orchestrator model** — Claude Opus for judgment, Sonnet for Scout? Or same model everywhere at first for simplicity?
2. **Scout timeout** — vm-pool's `vm_timeout` is 2h default. Match that, or tighter?
3. **Agent SDK invocation** — confirm how to drive a persistent Claude Code session with MCP tools programmatically. Verified during step 8.
4. **Orchestrator location** — dedicated VM vs. host process. Default: VM. Decide at step 8.
5. **Context management** — does the Agent SDK handle compaction, or do we need to manage it? Relevant once the session runs for hours.
6. **Spec template on the issue** — RFC suggests posting the Spec as a GH comment. For this PR: store in DB only, add GH comment posting as a follow-up.
7. **Re-exploration on reject** — what's the escape hatch if a task gets stuck in re-explore loops? For this PR: 3 attempts max enforced by the server (not the orchestrator), then mark task as `rejected`.
