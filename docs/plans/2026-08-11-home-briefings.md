# Home briefings: narrative project companion

*Plan only — approved direction from Nate 2026-08-11, not yet implemented.*
*Replaces the KPI-row Home (#789/PR #803) as the centerpiece; the mechanical
rows stay where they're actionable.*

## The reframe

The KPI row answered "how many"; nobody's question. The question Home should
answer is **"what's going on, and does anything need me?"** — the thing a
good engineering lead would tell you in 60 seconds after reading everything.
LLMs' unique advantage here is exactly that: they can *actually read
everything, every time* — every PR diff, every issue body, every transcript,
the git log — and synthesize across sources. No human does that standup prep;
it wouldn't make sense to pay a human to. So Home's centerpiece becomes three
generated briefings, each a short piece of prose with inline links.

## The three slots

1. **State of the project.** Is the repo active or quiet? What meta-projects
   / feature threads are being tackled right now (themes across recent PRs,
   issues, specs, commits — *named*, not counted)? Where is attention
   concentrated? What's the current bottleneck?
2. **Changes.** Open PRs and their real states (CI, mergeable, draft,
   review-waiting), what's gone stale and why that might be, branches/PRs
   that need cleanup, risky overlaps ("#812 and #815 both rewrite
   TranscriptView — land order matters"). Judgment, not thresholds.
3. **Issues.** What came in recently and what actually looks high-priority
   (inferred from content, not just labels), issue health (stale, probable
   duplicates, already-fixed-but-open), and what's worth queueing next given
   what's in flight.

**Tone contract (goes in the prompt, verbatim rules):** factual and terse; no
praise, no exclamation points, no "great progress" hustle framing; problems
and risks lead; "nothing notable" is a complete and welcome answer; every
claim links to its subject (markdown links — the app already renders them).
Each section ~100–150 words unless something is genuinely wrong.

## Architecture

**Briefing agents, not the orchestrator.** Each slot is generated by a
one-shot headless Claude Code run (`BRIEFING_CMD`), *read-only tooling only*:
`--allowedTools Bash(gh:*) Bash(curl:*) Bash(git log:*) Bash(git diff:*)` —
no write permissions, no `--dangerously-skip-permissions`. Fresh session per
generation (no context to maintain; the inputs ARE the context). The
orchestrator's long-lived chat stays a conversation, not a report mill.
The prompt per slot = tone contract + what to gather (gh queries, tasks API
endpoints, git log) + the server's cheap pre-known facts spliced in (pipeline
state, event high-water) so the agent spends its tool calls on GitHub-side
digging, which the server deliberately doesn't persist (query at decision
time — this whole feature is that rule made visible).

**On-demand + stale-while-revalidate, not a cron.** 3 slots × 4/hr × 24h
would be ~300 agent runs/day mostly generated for an empty room. Instead:

- `briefings` table (migration): `section PK, content, generated_at,
  event_high_water`. The persisted text is a *cache with a visible date*,
  never treated as truth — GitHub facts inside it were queried at
  generation time and are labeled with it.
- `GET /briefings` returns all three `{section, content, generated_at,
  stale, regenerating}`. If a section is past TTL (`BRIEFING_TTL_SECS`,
  default 900) the handler *returns the stale copy immediately* and kicks a
  single-flight background regeneration (per-section mutex — no stampede
  when the app fires three refreshes).
- Regeneration completion appends an event (`briefing_updated` kind or a
  `Note`) → SSE → app refetches. The nudge filter must EXCLUDE it
  (orchestrator reacting to briefings would be a feedback loop).
- App open = demand. App closed = zero generations. First open after a quiet
  night = stale copy instantly, fresh one ~30s later.
- Later optimization (not v1): skip regeneration when the event high-water
  hasn't moved AND a cheap `gh pr list --json updatedAt` probe shows no
  GitHub-side motion.

**Failure posture:** keep the last good briefing with its age; a failed run
sets a short cooldown and surfaces as "couldn't refresh (as of 40m ago)" —
never a blank slot, never a fabricated one.

## App changes

Home becomes (top to bottom):

1. **State of the project** — briefing prose (MarkdownView), "as of Xm ago"
   caption, subtle progress indicator while regenerating.
2. **Needs you** — KEPT as mechanical rows (specs awaiting verdict, failed
   builds). Instant, actionable, zero-latency truth; prose must not gate it.
3. **Changes** — briefing prose. The Recent-PR link rows fold into it (the
   agent links PRs inline; if that loses too much scannability, keep the
   rows under the prose).
4. **Issues** — briefing prose.

Velocity tiles: deleted (the spec itself documented the ~60-line removal
path; the held event log stays — Activity's incremental refetch and the
briefing prompts both use it).

## Follow-ups worth their own issues (not v1)

- **"Since you last looked":** briefings keyed to the reader's last visit —
  "while you were away: X landed, Y broke" — an actually-personal diff no
  static dashboard can do. Builds on `lastSeenSeq`, which already exists.
- **Briefing → action handoff:** "queue it" affordances on issue mentions
  (structured output alongside the markdown), bridging narrative to the
  pipeline API.
- Regeneration gating on real motion (event high-water + cheap gh probe).

## Cost note

Per generation: one small headless run with a handful of read-only tool
calls. Worst case with the app open all day: ~4/hr × 3 slots. The SWR +
single-flight design means the ceiling only applies while someone is
actually looking.
