# v2 resume: decisions + revised step order

Amends [2026-04-17-v2-diamond-1.md](2026-04-17-v2-diamond-1.md) after the
2026-08-09 review of v1 (`main`) and the v2 branch. Steps 1–6 of the original
plan are done and stand as-is.

## Decisions

**Resume the v2 branch.** v1 stays on `main` untouched until v2 runs its first
end-to-end loop; then v2 becomes the mainline.

**The Scout/Builder information barrier is inviolable.** The Builder never
sees Scout code. Two reasons, both load-bearing:

1. Reimplementing from the spec alone is what proves the spec is complete.
2. Specs are text, so they *compose*: a Builder run can take 1..N specs that
   overlap or batch naturally and implement them in a single branch against
   current main. Feature branches can never do this — at 70+ issues no tool
   keeps N branches conflict-free, but N documents merge trivially.

Diamond 2 data model must therefore assume a builder run references a *set*
of spec ids, not exactly one.

**Manual queue is human-authoritative.** There is always a manually
re-orderable queue over tasks/specs, adjustable at any moment. Hard rule from
the v1 desync audit: derived signals (labels → priority) are informational
only and must never clobber manual ordering. The poller never writes ordering
fields.

**Headless control API is the first interface, promoted ahead of everything
else.** Claude Code drives Tasks over HTTP while we build it — the API is the
dogfooding surface, the MCP server is a thin adapter over it, and any UI
comes later.

**UI: deferred, simple up front, mac-only.** Explicitly banned: vercel, next,
shadcn; no python. Anything else (native app, web UI, TUI, SwiftUI) is on the
table — pick whatever needs the fewest design decisions when the time comes.
Until then: API + CLI.

**Sync rules (from the v1 audit).** Never persist a GitHub-owned fact (PR
mergeable/SHA/CI, issue open-closed/labels) — query at decision time. Persist
only Tasks-owned state plus an append-only decision log keyed to immutable
SHAs. GitHub writes funnel through the server, never through agents.

## Vendor vm-pool (decided 2026-08-09)

tasks-vm comes back into this repo as workspace crates. Path deps across two
working trees gave none of the interface pressure of separation while blocking
atomic cross-cutting changes (and spec batching stops at a repo boundary).

- `../tasks-vm/crates/{client,pool,protocol,service,supervisor}` →
  `crates/vm-pool/<name>/`; `images/` → `images/`; `spec/spec.md` →
  `docs/vm-pool.md`
- Merge workspace deps (add `dirs`); path deps point in-repo; keep version
  fields so the crates stay publishable
- **Dependency-direction rule (the discipline that replaces repo separation):**
  vm-pool crates never depend on tasks crates. vm-pool stays pure
  infrastructure; app vocabulary enters only through the `AppProtocol` generic.
  Enforce in CI when CI exists; document in CLAUDE.md now.
- Old repo is archived as-is after the vendor lands (history preserved there);
  extract again via `git subtree` if/when vm-pool has outside users
- Sequenced AFTER the two in-flight changes land: the HTTP API (tasks) and the
  request/response correlation fix (tasks-vm working tree — vendored along
  with everything else)

   - Read: `GET /projects`, `GET /tasks` (queue order), `GET /tasks/:id`,
     `GET /sessions`, `GET /sessions/:id`, `GET /specs`, `GET /specs/:id`,
     `GET /spec-queue`, `GET /mode`, `GET /events?since=` (catch-up) +

     `POST /queue/reorder` (explicit task-id order → manual_rank),

   - Schema: add `tasks.manual_rank INTEGER NULL`; `list_tasks` orders by
     manual_rank (nulls last), then priority desc, then ingested_at
   - CLI: `tasks serve`, `tasks add-project`, plus thin curl-equivalent
     subcommands hitting the API
8. **MCP tool server** — orchestrator tools as an adapter over the same
   store/API operations
9. **Container image `agent:v1`** — supervisor + Claude Code + toolchain
10. **Orchestrator session** — tick-based `claude -p --resume <session-id>`
    per notification batch, HTTP MCP config pointing at the tasks server;
    graduate to an SDK sidecar only if mid-turn control becomes necessary

## Dogfooding target

As soon as 7 + 9 + 11 exist (orchestrator optional — a human or Claude Code
session can play orchestrator through the API), point Tasks at its own repo
and let Scouts produce specs for the remaining work.
